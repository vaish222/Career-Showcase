The Problem
Pantry to Plan was designed to turn a pantry photo into a 3–5 day dinner plan and a consolidated shopping list. The product combines image-based ingredient detection, user preferences, recipe retrieval, pantry depletion, and shopping-list aggregation in one workflow.    README (1)
A key challenge was making the experience trustworthy and usable. AI-generated pantry detections could be incomplete or inaccurate, so users needed a clear way to review and correct what the system detected before meal planning began.
The team also needed a reliable way to evaluate whether the planner was actually following constraints and producing mechanically correct results rather than simply generating plausible-looking output.
My Role
My ownership focused on the product experience, documentation, and evaluation quality.
I worked on:
- UX enhancements and flow refinement
- Human-in-the-loop pantry confirmation experience
- README and developer run documentation
- Golden evaluation dataset creation
- Running evals and validating results
How I Approached It
I approached the project from two perspectives: make the product easier to use and make its behavior easier to evaluate.
For the UX, I helped improve the flow so users could review and correct pantry items before the planner used them. The confirmation step lets users see detected ingredients, confidence, mapping status, and quantity, while low-confidence or incomplete detections are surfaced for additional review.    README (1)
This created an explicit human checkpoint between AI perception and downstream planning instead of assuming the model was always correct.
I also updated the README so a new developer could understand the project architecture, environment setup, how to run the Streamlit application, and how the retrieval and fallback paths worked. The documentation covers local setup, application launch, retrieval behavior, and the overall product flow.    README (1)
For evaluation, I helped create the golden dataset and run evals across both standard and edge-case scenarios. These scenarios included vegetarian constraints, sparse pantries, tight calorie bands, noisy vision inputs, and other planning conditions.    README (1)
Key Product Decisions
- Require users to review AI-detected pantry items before planning
- Surface low-confidence detections instead of hiding uncertainty
- Make the setup and run process clear enough for another developer to reproduce the application
- Create a golden dataset to define expected system behavior
- Evaluate hard constraints and system correctness separately from subjective recipe quality
- Use repeatable evals to measure whether product changes actually improve behavior
Technical / System Context
The application uses:
- GPT-4o for pantry image understanding
- Pinecone and embeddings for recipe retrieval
- Python for deterministic scoring, constraints, pantry depletion, and shopping-list calculations
- Streamlit for the user experience
- Pydantic schemas for structured system contracts
- LangSmith for evaluation workflows    README (1)
The user experience follows a four-step flow:
Upload pantry photo → Confirm and edit ingredients → Set preferences → Generate meal plan and shopping list    README (1)
Evaluation & Quality
I helped create a golden evaluation dataset that could be used repeatedly to check whether the planner behaved as expected.
The evaluation suite validates concrete system behaviors such as:
- vegetarian constraints are never violated
- calorie calculations are correct
- pantry inventory never goes negative
- shopping lists contain only actual shortages
- invalid schema values are rejected
- incomplete plans are only allowed when hard constraints prevent completion    README (1)
The project also includes a LangSmith evaluation harness so individual golden cases can be executed and traced consistently.    README (1)
Outcome / Impact
The project delivered an end-to-end AI meal-planning experience with a clear human review step and a repeatable evaluation framework.
It won 1st place at The Gen Academy Mastering Agentic AI Demo Day.

What I Learned
One of my biggest takeaways was that building an AI product is not only about model capability.
The surrounding product experience matters just as much.
Users need a way to correct AI mistakes. Developers need clear documentation to reproduce the system. Teams need repeatable evals to know whether a change actually improves the product.
Creating the golden dataset reinforced an important lesson for me:
AI quality should be defined before it is measured.
Once expected behaviors and hard constraints are explicit, product iterations become much easier to evaluate objectively
